# AI-Friendly API

## Abstract

This spec defines the conventions that make Everruns' HTTP API legible and
self-driving for LLM agents — both the agents we host and the agents that
consume Everruns from the outside (via OpenAPI tool calling, the MCP
`execute`/`query` endpoints, or A2A). It complements [`specs/apis.md`](apis.md)
(routing, status codes, lifecycle) with rules about *content shape* and
*discoverability*.

Reference: ["Towards AI-Friendly Web APIs"](https://chaliy.name/blog/towards-ai-friendly-web-apis/).

## Why

The same API is consumed by three audiences with different needs:

1. **Humans** writing integrations — read docs, run sample requests, infer.
2. **Hosted agents** inside Everruns — call our own API as a tool.
3. **External agents** — call Everruns via OpenAPI tool calling, MCP, or A2A.

For audiences 2 and 3 the OpenAPI spec *is* the documentation. There is no
"read the prose and intuit it" step. Every field name, description, error
message, and link the agent needs to make its next move must be present in the
response or recoverable from the schema. Anything an agent cannot derive
without out-of-band knowledge is a defect.

## Principles

Six principles, adopted from the reference post and adapted to Everruns:

### 1. Semantic Operations

Endpoints describe business intent, not CRUD primitives, and every operation
has a stable, descriptive `operationId` that maps 1:1 to an agent tool name.

- Action endpoints already follow this: `POST /v1/sessions/{id}/cancel`,
  `POST /v1/agents/{id}/copy`, `POST /v1/harnesses/preview`,
  `POST /v1/agents/{id}/delete` (dangerous), etc.
- `PATCH` is preferred over `PUT`-as-state-replace for partial updates.
- `operationId` MUST be set on every utoipa `#[utoipa::path]`. Format:
  `verb_resource[_qualifier]`, e.g. `list_agents`, `cancel_session`,
  `preview_harness`, `dangerous_delete_agent`. The same `operationId` is what
  the MCP `execute`/`query` catalog surfaces; renaming one is a public-surface
  change.

### 2. Self-Sufficient OpenAPI

The OpenAPI document is the contract. Agents perform "preflight thinking"
against it before sending a request.

- Every request DTO field carries a `description` covering: what it is, where
  the value comes from (which endpoint produced it), allowed range/enum, and
  whether it's required.
- Every response DTO field carries a `description` covering: what it means,
  unit/format, and (where ambiguous) what `null` signals.
- Examples (`example = ...`) are populated on every non-trivial field
  (timestamps, IDs, enums, free-text intents).
- Enums prefer string variants over magic ints, and the schema lists every
  variant.
- The exported spec lives at `/api-doc/openapi.json` and is regenerated by
  `./scripts/export-openapi.sh`. PRs that change the surface MUST refresh it.

### 3. Domain Assumptions in the Schema

Agents only know what we tell them in the schema. The ubiquitous language of
[`specs/concepts.md`](concepts.md) — Agent, Harness, Session, Skill, Capability,
App, Channel, Run, Turn — MUST be used consistently in field names, parameter
names, and descriptions. Lifecycle states (active / archived / deleted, see
[`specs/apis.md`](apis.md#building-block-lifecycle-api-rules)) MUST be named
explicitly in the schema, not inferred from boolean flags. Cross-entity
relationships (e.g. "harness inherits from parent_harness_id") get one sentence
of prose in the field description, not a separate page of docs.

### 4. Actionable Error Responses (RFC 9457)

Error responses today follow `{ "error": "...", "status": 400 }` (see
[`specs/apis.md`](apis.md#error-responses)). Going forward, REST error
responses adopt the RFC 9457 *Problem Details* shape, served as
`application/problem+json`:

```json
{
  "type": "https://errors.everruns.com/validation/agent-name-too-long",
  "title": "Validation failed",
  "status": 422,
  "detail": "Agent name exceeds the 200-character limit.",
  "instance": "/v1/agents",
  "code": "agent_name_too_long",
  "allowed_actions": [
    {
      "rel": "retry",
      "operation_id": "create_agent",
      "hint": "Shorten 'name' to <= 200 chars and resubmit."
    }
  ],
  "retry_after_seconds": null
}
```

Required fields: `type`, `title`, `status`. Conventional extensions:

- `code` — stable, machine-readable error code. Snake_case. The set of codes
  is documented per-resource in the OpenAPI schema, not invented per
  call-site.
- `detail` — human/agent readable explanation. MUST NOT leak provider names,
  internal error chains, or stack traces. The [`public-endpoints.md`](public-endpoints.md)
  sanitization rules continue to apply.
- `allowed_actions` — array of `{ rel, operation_id, hint, href? }` entries
  telling the agent what to do next. Examples:
  - `409 already_exists` → `{ "rel": "get-existing", "operation_id": "get_agent", "href": "/v1/agents/abc" }`
  - `429 rate_limited` → `{ "rel": "retry-later", "operation_id": ..., "hint": "wait retry_after_seconds" }`
  - `403 archived` → `{ "rel": "unarchive", "operation_id": "update_agent", "hint": "set archived=false" }`
- `retry_after_seconds` — set on `429` and transient `503`.
- `instance` — the request path (no query string secrets).

Existing endpoints keep emitting the legacy `{ error, status }` body during a
deprecation window; new endpoints SHOULD emit Problem Details directly. A
transitional middleware MAY emit both shapes (Problem Details fields plus
legacy keys) until callers migrate. Public-endpoint payload errors continue to
flow through `PublicError` ([`public-endpoints.md`](public-endpoints.md)) —
sanitization wins over expressiveness for unauthenticated callers, so the
`allowed_actions` array on public endpoints is empty or omitted unless the
action is itself public.

### 5. Hypermedia for Navigation

Everruns already injects `self_url` / `view_url` / `ui_link` into JSON
responses via the link decoration middleware in
`crates/server/src/api/common.rs` (`decorate_json_response_links`). Going
forward this is treated as a first-class affordance, not an MCP-only nicety:

- Every entity response carries `self_url` (canonical API URL) and `view_url`
  (canonical UI URL). The MCP `ui_link` alias is kept for backward
  compatibility.
- Nested entity references get the same treatment recursively.
- Collection responses include `pagination` with `next` / `prev` URLs when
  applicable, not just opaque cursors.
- Each resource exposes a `config` endpoint
  (`GET /v1/{resource}/config`, [`specs/apis.md`](apis.md#resource-config-endpoints))
  whose response advertises which actions the caller is permitted to perform.
  This *is* the agent-facing capability discovery surface and MUST stay
  accurate as policies evolve.
- Enums that drive other endpoints (model IDs, harness types, channel kinds,
  regions, locales) MUST be reachable via a list endpoint, not only via the
  OpenAPI enum. Agents should be able to ask "what values are valid right
  now?" at runtime.

### 6. Human Representations

Distinguish system identifiers from human-facing names so agents know which
field to show in a chat reply vs which to pass back to the API:

- System IDs use the prefixed-ID format from [`specs/id-schema.md`](id-schema.md)
  (`agent_…`, `sess_…`, `harn_…`). These are the only values legal in foreign
  key positions.
- Display fields use `name`, `title`, `display_name` — descriptions MUST state
  "safe for user-facing messages".
- Schemas SHOULD NOT mix the two by overloading a single field. Where legacy
  endpoints do (e.g. `name` doubling as a slug), the description must call it
  out explicitly.

## Additional Techniques

- **Workflow metadata.** Multi-step flows (e.g. session create → first
  message → SSE subscribe) are documented in [`specs/apis.md`](apis.md) and
  linked from the relevant `operationId` descriptions. Tooling-readable
  workflow metadata (OpenAPI 3.1 `x-workflow` or Arazzo) is a future option;
  for now prose in the description is sufficient.
- **OpenAPI overlays.** Agent-tuned views (denser examples, fewer optional
  fields surfaced) are emitted via an overlay applied at export time rather
  than by forking the spec.
- **Discovery.** `/api-doc/openapi.json` is the canonical entry point. A
  future `/.well-known/api-catalog` (RFC 9727) may aggregate OpenAPI, MCP, and
  A2A endpoints.

## Current State vs Target

| Principle | Current | Gap |
|---|---|---|
| Semantic operations | Action endpoints exist; `operationId` not enforced | Audit utoipa annotations; enforce `operationId` lint |
| Self-sufficient OpenAPI | Mixed — some fields lack descriptions/examples | Add a CI check that fails on undocumented schema fields |
| Domain language | Used in code; not always echoed in descriptions | Refresh descriptions per the [`specs/concepts.md`](concepts.md) glossary |
| Actionable errors | `{ error, status }` flat shape | Adopt Problem Details with `code` + `allowed_actions` |
| Hypermedia | `_link` / `self_url` decoration exists, plus `config` endpoints | Document the contract; extend to pagination URLs |
| Human representations | Prefixed IDs ([`specs/id-schema.md`](id-schema.md)) + `name`/`title` fields exist | Document the rule explicitly in schemas |

## Adoption Checklist

When touching an API surface, the contributor:

1. Sets `operationId` on every new `#[utoipa::path]`.
2. Adds `description` and `example` to every new schema field.
3. Returns RFC 9457 Problem Details for new error paths, with `code` and
   (where applicable) `allowed_actions`.
4. Includes `self_url`/`view_url` on returned entities (the middleware
   handles most cases automatically; manual responses must opt in).
5. Re-runs `./scripts/export-openapi.sh`.
6. Refreshes the relevant section of [`specs/apis.md`](apis.md).

## Threat Model

This spec adds detail to API responses (error codes, allowed actions,
self-links). Categories from [`specs/threat-model.md`](threat-model.md) to
keep in mind:

- **TM-INFO-001 (Information disclosure)** — Problem Details MUST NOT widen
  the leak surface. `detail` and `code` are bounded by the same sanitization
  rules as today. Public endpoints stay on `PublicError`.
- **TM-AUTHZ-005 (Tenant isolation)** — `allowed_actions` only references
  operations the caller is already authorized to perform; never advertise a
  cross-tenant resource.

## Non-Goals

- Replacing OpenAPI with a bespoke schema language.
- A separate "AI" version of the API on a different prefix. The same API
  serves humans and agents; AI-friendliness is achieved through quality of
  the canonical surface, not parallel surfaces.
- Mandating hypermedia clients. Agents that ignore `_links` and reconstruct
  URLs from the OpenAPI spec must keep working.
