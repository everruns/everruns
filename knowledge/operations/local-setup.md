# Local Setup and Kubernetes

Status: accepted (2026-10-24). `everruns docker` shipped; `upgrade`/`reset`
subcommands and the Helm chart are next.

## Goal

A person with Docker types `everruns docker up`, answers at most three
questions, and gets a healthy Platform with the browser UI and the CLI both
working against it. Before this, the [Docker Compose guide](../../docs/getting-started/docker-compose.md)
took about ten manual steps, including three secrets generated by hand.

## Decisions

| Decision | Why |
|---|---|
| A subcommand group of the existing CLI (`crates/cli/src/commands/docker/`), no new crate | The CLI is already installed (Homebrew); the crate policy keeps the crate count down. |
| Docker Compose, not a native binary | DEV_MODE's embedded PostgreSQL deletes its data on exit and refuses root, the UI is a separate Next.js server, and there is no macOS server binary. A Docker-free mode waits until people ask for it. |
| Named `docker` | It names what runs the stack, so a later Docker-free mode can take its own name. |
| Shell out to the `docker` CLI | It already knows the person's context and socket (Docker Desktop, OrbStack, Colima); no daemon client to add. `EVERRUNS_DOCKER` swaps in a compatible CLI such as Podman. |
| One compose file | The CLI embeds a copy of `examples/docker-compose-full.yaml` (`crates/cli/assets/`, kept identical by a test) and runs it without profiles; the guide turns on `scale` and `metrics`. Compose Smoke tests both. |
| `up` converges, it does not script a first run | Each step checks before acting: secrets are generated once, answers are asked once, containers that did not change are left running, a working CLI token is reused. A lock file makes concurrent runs take turns. Re-running is the repair path. |
| No upgrade as a side effect | Images follow the CLI version on first setup. Later, `up` reports a newer CLI and moves only with `--image-tag`, because a new image runs migrations. |
| Shell values never override the saved setup | Compose prefers the shell environment over `.env`; `up` removes the variables it manages from the child environment. |

### Who signs in

Asked at setup (`--auth`), mapped onto the server's auth modes:

| Answer | Server | Consequences |
|---|---|---|
| `single` (default) | `admin` | One generated admin password. Default provider keys are copied into the default organization (`SEED_DEFAULT_PROVIDER_KEYS_FROM_ENV`). |
| `none` | `none` | The server refuses this outside `DEPLOYMENT_GRADE=dev`, so the instance runs as dev, which also enables experimental features. The port binds 127.0.0.1 only. |
| `accounts` | `full` | Signup is open, so the server refuses to share default provider keys; `--provider` does not apply. The CLI registers the admin account and creates its organization. |

The CLI signs itself in with a personal access token it creates, not the
password, so a password changed in the UI does not log the CLI out.

### What is kept

The instance folder (data dir `everruns/docker/<name>/`) holds `.env` (0600,
the only record of the setup, including the encryption key) and
`compose.yaml`. The database is a Docker volume named after the Compose
project. Losing `.env` makes stored provider keys and secrets unreadable.

### CLI profile

`up` writes profile `local` (`local-<name>`) and makes it current, asking first
when another profile is current. For this to mean anything, the CLI resolves
its profile as `--profile`, then `EVERRUNS_PROFILE`, then the profile signed in
to last, then `default`; before, it always used `default` unless told
otherwise.

## Kubernetes: Helm chart, not an operator

An operator pays for itself when software needs ongoing ordered actions a
Deployment cannot express. Everruns needs none today:

- PostgreSQL is the only stateful part; managed databases or CloudNativePG own
  its lifecycle better than anything written here.
- The server applies migrations itself at start, under an advisory lock.
- The server runs as one replica by design (per-process session SQL store and
  mounts); workers scale on queue depth, which KEDA does without custom code.
- Agents and sessions live in the database behind the API with change history;
  mirroring them as custom resources would make a second source of truth.

So the plan is an official Helm chart published as an OCI chart: server
(one replica, `Recreate`), workers with optional KEDA scaling, UI, Caddy with
the same routes as Compose, external PostgreSQL by default, optional NATS and
Valkey, and secrets that are generated once and kept across `helm upgrade`
(regenerating the encryption key would make stored secrets unreadable).

Revisit an operator if many teams run many instances per cluster and want to
declare them as objects. Agent sandboxes as pods would be a sandbox provider,
not an operator.
