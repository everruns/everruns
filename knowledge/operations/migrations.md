# Migrations Specification

## Abstract

PostgreSQL schema migrations live in `crates/server/migrations/`. They use SQLx's built-in migration runner and auto-apply on server startup, including DEV_MODE, which migrates a fresh embedded database.

## Naming Convention

```
YYYYMMDDHHMMSS_<description>.sql
```

- `YYYYMMDDHHMMSS`, UTC creation time, which becomes the sqlx version. This is sqlx's own default naming.
- `<description>`, lowercase feature name (letters, digits, underscores).
- Create one with `just new-migration <description>`.

The lowest version is the **baseline**, `20261011000000_baseline.sql`: the schema and seed rows
that the old sequential history `001..222` produced, generated with `pg_dump`. See Baseline below.

### Why timestamps

Sequential numbers made every open branch pick "highest on main + 1". Each PR passed CI alone, and
parallel merges landed one number two or three times (215 twice, 218 three times on 2026-10-11).
Two files with one version fail sqlx startup, and the repair (renaming a merged file) breaks any
database that already applied the old name, since sqlx then sees a different checksum for that
version (`VersionMismatch`). Creation timestamps make collisions practically impossible.

sqlx applies every version missing from `_sqlx_migrations`, in version order, without requiring
new versions to be above the highest applied one. A branch that merges after a newer-timestamped
one still applies. The cost is that two environments may apply two parallel migrations in a
different order, which only matters when both change the same objects in dependent ways; review
such pairs as one change.

## Development Workflow

Run `just new-migration <description>` and write the SQL. After a rebase there is nothing to
renumber. If a rebase pulls in a migration your branch depends on that is newer than yours, create
your migration again so it sorts after it.

## Baseline

A fresh database used to replay 222 files. On 2026-10-11 they were squashed into the baseline,
generated by applying `001..222` to an empty database and dumping it (`pg_dump --no-owner
--no-privileges --column-inserts`, with session `SET`s made `SET LOCAL` and psql meta-commands
removed). The seed rows it carries (default organization, system principal, durable counters,
plugin marketplace) have the ids and timestamps of that run.

The legacy files stay, unchanged, in `crates/server/migrations/legacy/`. sqlx's `migrate!` reads
only the top directory, so they never run as part of the current set. They exist for **adoption**
(`crates/server/src/setup/migrations.rs`): on a database whose `_sqlx_migrations` holds legacy
versions, the server first applies any legacy migrations it is missing, then, under an advisory
lock, replaces the 222 legacy rows with one row for the baseline (its real checksum). The baseline
SQL never runs there. Every real migration path goes through that code: server startup and the
`everruns-migrate` binary that the admin container's `migrate` command runs. Plain
`sqlx migrate run` on a legacy database fails with `VersionMissing` and changes nothing.

Consequences:

- A binary from before the baseline refuses to start on an adopted database (`VersionMissing`
  for the baseline version), the same as any binary older than its database.
- `crates/server/tests/domain/migration_baseline_test.rs` keeps the baseline honest while the
  legacy directory exists: a legacy database and a baseline database must have the same schema
  objects and row counts, and full and partial legacy databases must adopt.
- Tests of historical data conversions (`create_database_migrated_before`) replay the legacy
  history, so they keep working.

Remove `legacy/` and the adoption code once no deployment can still be on the legacy history.
A later squash would follow the same pattern with a new baseline version.

## Immutability

Do not rename, rewrite, or delete a merged migration. SQLx records each migration's version,
description, and checksum in `_sqlx_migrations`; changing one that a database applied breaks
startup there. The only exception is the content-identical move of `001..222` into `legacy/`,
allowlisted in `scripts/lib/check-migration-immutability.sh`.

`crates/server/tests/domain/migration_history_test.rs` locks specific historical filenames and SQL bodies that must not change.

## Name Validation

`scripts/lib/check-migration-ordering.sh` is the single validator: the baseline is the lowest
version, `legacy/` holds exactly 001..222, every other file is `YYYYMMDDHHMMSS_<description>.sql` with a valid UTC time, and no two
files share a version. CI runs it on every PR and on every push to `main` (job
`Migration Immutability`), so a duplicate that two parallel merges create shows up on the next
main run. `just pre-push` and `just pre-pr` run it too; `scripts/test-migration-ordering.sh`
covers it.

## Execution

- **Framework:** SQLx `migrate!()` macro behind `crates/server/src/setup/migrations.rs`, which also adopts legacy databases
- **Auto-apply:** on startup, into the embedded database in DEV_MODE too (skippable via `--no-migrations` outside DEV_MODE)
- **Tracking table:** `_sqlx_migrations` (version, description, checksum, installed_on)
- **Build integration:** `crates/server/build.rs` watches the migrations directory so binaries rebuild when migrations change

## Conflict Resolution

Two branches no longer compete for a number. If the validator ever reports a shared version, give
the newer file a fresh timestamp before it merges; once merged, follow Immutability and add a new
migration instead of renaming.
